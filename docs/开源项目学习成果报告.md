# 开源工程计算项目学习成果报告

> 检索日期：2026-07-25
> 适用项目：工程计算自动化平台（当前以建筑电气计算为主，后续可扩展给排水、暖通、消防等专业）

## 一、报告目的

本报告记录对 GitHub、PyPI、项目官方网站等公开资料的检索结果，提炼可用于本项目的架构、计算表达、测试和报告生成方法。

本次检索没有发现能够直接覆盖“国内建筑机电计算 + 规范依据追溯 + Excel 批量输入 + 计算书输出 + 人工复核状态”的成熟开源项目。因此，本项目不采用整体复制路线，而采用“吸收成熟方法、保持自身业务边界”的路线。

## 二、项目定位判断

本项目当前已经形成以下核心边界：

- 本地 Windows Web 工具；
- 项目、回路和计算历史保存；
- Excel 批量导入与结果导出；
- 负荷、压降、短路等电气计算模块；
- 输入、计算步骤、中间结果、告警和参数来源可追溯；
- 计算依据未经核实或批准时，不把暂算结果升级为正式结论。

因此，最应该借鉴的是“工程计算工作流”和“可复核计算书”的实现方式，而不是盲目引入大型 BIM 或电力系统平台。

## 三、重点学习成果

### 1. Calcpad：学习计算表达和计算书生成

项目：[Proektsoftbg/Calcpad](https://github.com/Proektsoftbg/Calcpad)

Calcpad 是与本项目目标最接近的参考项目。它将变量、单位、公式、条件、循环、表格和文字说明放在同一计算工作流中，并支持 HTML、PDF、Word 等输出。

可借鉴内容：

- 计算过程不只保存最终结果，同时保存公式、变量代入和中间结果；
- 计算模块与报告生成相互分离；
- 统一处理单位、变量、舍入和结果显示；
- 计算输入可以批量化，结果可以形成正式计算文档；
- 计算过程适合采用“输入 → 公式 → 中间值 → 校核 → 采用值”的固定结构。

对本项目的落地结论：

- 保留现有 Python 纯函数计算核心，不引入 Calcpad 自有语言；
- 继续强化 `reports.py`，让每个计算模块输出结构化步骤；
- PDF 计算书应展示原始输入、公式、中间值、结果、告警和参数来源；
- 将报告模板作为独立层维护，避免把公式写死在 HTML 模板或 Excel 单元格中。

许可证：MIT。许可证允许商业使用、修改和再发布，但如直接复制代码仍需保留版权和许可证声明。

### 2. Blueprints：学习工程计算模块化和测试组织

项目：[Blueprints-org/blueprints](https://github.com/Blueprints-org/blueprints)
文档：[Blueprints Documentation](https://blueprints.readthedocs.io/)

Blueprints 是 Python 工程计算包，重点在于将工程公式、材料数据、规范检查和测试组织成可复用模块。

可借鉴内容：

- 每个工程计算模块有清晰的输入、输出和适用范围；
- 公式实现与界面、数据库和报告解耦；
- 通过正常值、边界值、非法输入和极端值建立测试；
- 文档、测试和代码一起维护；
- 对“不适用”与“无法判断”保持明确区分。

对本项目的落地结论：

- 每个计算模块统一实现 `输入模型 → 校验 → 计算 → 结果模型`；
- 将“缺失值、零值、不适用、未核实”保持为不同状态；
- 每个模块至少建立正常样本、边界样本、错误输入和极端样本；
- 将规范版本、参数来源和样本日期作为计算结果的组成部分；
- 计算函数不能依赖页面请求、SQLite 查询或 Excel 单元格。

许可证：MIT。

### 3. handcalcs：学习“公式—代入—结果”的可读输出

项目：[handcalcs PyPI](https://pypi.org/project/handcalcs/)

handcalcs 的价值不在于替代本项目，而在于它强调工程师熟悉的计算表达：先展示符号公式，再展示数值代入，最后展示结果。

可借鉴内容：

- 计算书中保留公式，而不是只输出数字；
- 让中间结果具备工程师可读性；
- 计算逻辑仍由代码执行，展示层负责将其转换为文档表达。

对本项目的落地结论：

- 不直接依赖 Jupyter/LaTeX 作为主界面；
- 在现有结果模型中增加公式文本、代入值和单位字段；
- PDF 输出优先保证复核便利，而不是追求复杂排版；
- 对每个关键计算步骤保留可展开的中间结果。

### 4. VeraGrid 和 PyPSA：作为后续复杂电力计算的算法参考

项目：[VeraGrid](https://github.com/SanPen/GridCal)
项目：[PyPSA](https://github.com/PyPSA/PyPSA)

这两个项目主要面向电力系统建模、潮流、短路、优化和网络分析，规模和适用对象明显大于当前建筑单体电气计算工具。

可借鉴内容：

- 设备、节点、支路和网络拓扑的对象化建模；
- 计算方法与输入数据、结果数据分离；
- 对复杂网络计算提供标准化结果对象；
- 通过示例网络和回归测试验证算法。

暂不引入的原因：

- 当前项目首期重点是建筑电气回路和工程计算书，不是电网仿真；
- 引入大型电力系统模型会增加数据结构和验证成本；
- 不能因为已有短路计算，就直接把项目扩展为完整电力系统平台。

### 5. IfcOpenShell 和 FreeCAD：作为未来 BIM/几何联动参考

项目：[IfcOpenShell](https://github.com/IfcOpenShell/IfcOpenShell)
项目：[FreeCAD](https://github.com/FreeCAD/FreeCAD)

二者分别代表 IFC 数据处理和开源参数化建模方向，适合未来从 BIM、模型或几何数据中提取工程计算输入。

可借鉴内容：

- 使用标准化对象模型保存建筑构件和属性；
- 将模型数据提取层与计算层分离；
- 对外部模型输入进行明确的数据映射和校验。

暂不引入的原因：

- 当前项目尚无稳定的 BIM 输入需求；
- DWG/IFC 自动识别存在对象、图层、命名和拓扑不一致问题；
- 在计算样本不足时接入 BIM，会扩大问题范围而不能提高计算可信度。

## 四、形成的推荐架构

综合以上项目，建议本项目继续采用以下结构：

```text
页面 / Excel / CSV 输入
        ↓
字段校验与单位归一化
        ↓
独立计算模块
        ↓
约束校核与告警
        ↓
结构化计算步骤与结果
        ↓
SQLite 历史记录 / Excel 汇总 / PDF 计算书
```

每个计算模块建议固定包含：

```text
模块名称
适用范围与不适用范围
输入字段、单位、必填性、来源
参数版本和来源
公式与计算步骤
结果、采用值、告警
正常样本、边界样本、错误样本
```

## 五、建议优先落地的改进

### P0：计算结果结构化

统一每个模块的结果结构，至少包括：

- 输入快照；
- 参数来源；
- 计算步骤；
- 中间结果；
- 校核结果；
- 告警；
- 采用值；
- 模块版本。

### P1：计算书表达升级

参考 Calcpad 和 handcalcs，逐步让 PDF 计算书同时展示：

```text
原始输入 → 公式 → 数值代入 → 中间结果 → 校核 → 采用值
```

### P1：测试样本体系

参考 Blueprints，为现有模块补充四类测试：

- 正常工程样本；
- 最小/最大边界样本；
- 缺失值、单位错误和非法输入；
- 极端值和不适用条件。

### P2：设备库和规范依据版本化

设备参数、规范条文、厂家资料和人工样本不应混在计算代码中。应独立记录名称、版本、日期、来源和核实状态。

## 六、明确不采用的做法

- 不直接复制其他项目的专业公式和参数；
- 不把国外标准的计算逻辑直接当作国内规范结论；
- 不为了“功能完整”提前接入 BIM、DWG 自动识别或多专业综合平台；
- 不用最终数字替代计算过程和参数来源；
- 不把未经人工核实的开源算法直接用于正式工程结论；
- 不因某个开源项目有较多 Star，就判断其适合本项目的业务场景。

## 七、最终学习结论

本次学习形成的核心结论是：

1. 本项目最值得建设的不是“大而全的计算软件”，而是可复核、可追溯、可批量运行的工程计算流水线。
2. Calcpad 提供了计算书和计算表达的参考方向；Blueprints 提供了模块化和测试体系的参考方向；handcalcs 提供了中间过程可读性的参考方向。
3. VeraGrid、PyPSA、IfcOpenShell 和 FreeCAD 应作为后续专项能力的参考库，当前不宜成为项目依赖。
4. 本项目的真正差异化不在于重新发明公式，而在于把个人反复使用的计算过程、输入校验、依据追溯、复核状态和结果输出固化起来。
5. 后续每增加一个计算模块，都应先满足“样本可核实、参数可追溯、结果可复核”，再考虑扩展功能。
