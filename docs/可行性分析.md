# 工程计算自动化可行性分析

> 分析日期：2026-07-23  
> 结论性质：立项前可行性判断，不是计算依据或规范审查结论。

## 一、结论先行

### 总体结论：有条件可行，建议立项，但必须缩小首期范围

“工程计算自动化”在技术上没有明显障碍，业务上也有直接价值。真正的难点不在公式编码，而在以下三件事：

1. 计算边界是否定义清楚；
2. 采用参数和设备数据是否可信、可追溯；
3. 是否有足够的正确样本证明程序结果可靠。

因此，不建议把首期目标定为覆盖“负荷计算、管径计算、设备选型”的综合平台。建议先完成一个高频单项计算的闭环，再决定是否扩展。

推荐的首期闭环：

> 给定流量及管道条件 → 候选管径计算 → 流速/阻力校核 → 设计需求汇总 → 计算书导出

如果使用者的实际高频任务不是这一项，则应以真实工作量排名替换，但仍保持“一次只做一个闭环”。

### 当前立项评级

| 维度 | 评分 | 判断 |
|---|---:|---|
| 技术可行性 | 4.5/5 | Python、Excel 和现有开源计算能力足够 |
| 业务可行性 | 4/5 | 重复录入、重复计算和复核成本真实存在 |
| 数据可行性 | 2.5/5 | 当前项目目录没有可直接用于回归验证的计算样本 |
| 使用可行性 | 4/5 | Excel 输入输出符合现有工程习惯 |
| 维护可行性 | 3/5 | 取决于是否控制模块数量并管理参数版本 |
| 综合判断 | 3.6/5 | 可以启动验证版，暂不承诺综合平台 |

评分表示当前项目条件，不表示专业计算本身的准确程度。

## 二、为什么值得做

### 1. 项目价值并不是“替代现有设计软件”

现有商业软件已经能够完成大量通用计算和设计联动。例如：

- 天正暖通已经提供负荷计算、水力计算、设备选型和计算书输出，并强调与图形、建筑信息联动。[天正 T30 暖通官方介绍](https://tangent.com.cn/tzt30nt)
- 浩辰暖通提供从房间信息提取、负荷计算到多联机设备及管径选型的流程，并允许扩充设备数据库。[浩辰 CAD 暖通官方介绍](https://www.gstarcad.com/product/gstarcad_hva/2026/)
- 广联达数维机电设计提供从房间参数、负荷计算、设备选型到管网计算和模型更新的一体化能力。[广联达数维机电设计官方介绍](https://www.glodon.com/product/414)
- Revit 能按管道几何、粗糙度及流体属性计算压力损失，并支持管径计算和闭式水系统分析。[Autodesk 管径计算说明](https://help.autodesk.com/cloudhelp/2022/ENU/Revit-MEPEng/files/GUID-E1121308-E1E5-4AF1-B2FA-913CBD35F656.htm)、[Autodesk 压力损失说明](https://help.autodesk.com/cloudhelp/2024/ENU/Revit-MEPEng/files/GUID-B3A3BB94-5223-4318-8DB4-E1CDE85C62E0.htm)

因此，本项目如果只是复制通用公式，竞争力有限。它的合理定位应是：

- 固化使用者反复使用的计算过程；
- 兼容已有 Excel 数据和成果格式；
- 让参数来源、中间过程和采用值更容易复核；
- 把多个零散计算表连接起来；
- 对商业软件不顺手或无法定制的“小而高频”环节补位。

### 2. 价值最高的不是“按一下计算”

单个公式本身通常不耗时。实际节省来自：

- 不再重复录入相同项目数据；
- 自动完成单位换算和批量计算；
- 输入变化后关联结果统一刷新；
- 自动生成汇总、错误清单和计算书；
- 设备筛选能够说明未通过原因；
- 计算版本和参数来源可追溯。

如果仅做若干独立网页计算器，使用价值可能偏低；如果打通“输入—计算—校核—输出”，价值明显更高。

## 三、各类功能的可行性

### 3.1 管径及阻力计算

### 判断：高可行，最适合作为首期

有利条件：

- 输入、输出和中间过程容易定义；
- 可从单管段开始，逐步扩展至枝状管网；
- 结果容易与手算表或现有软件交叉核对；
- 能直接衔接泵的流量、扬程需求；
- Python 生态中已有流体性质及管网计算基础。

CoolProp 能提供流体、湿空气、不可压缩流体及水/蒸汽等物性；其官方文档也给出了 Python 接口和适用范围。[CoolProp 官方文档](https://coolprop.org/contents.html)  
pandapipes 提供基于表格数据的稳态热工水力管网模型，包含管道、阀门、泵、换热器等组件，适合后期研究网络求解，但其定位更偏区域供热和燃气网络，不能直接视为国内建筑机电计算模块。[pandapipes 官方文档](https://pandapipes.readthedocs.io/en/latest/)

分阶段建议：

| 层级 | 内容 | 可行性 | 首期是否纳入 |
|---|---|---:|---|
| L1 | 单管段流速、沿程及局部阻力 | 高 | 是 |
| L2 | 多管段顺序计算、最不利路径汇总 | 高 | 是，样本具备后 |
| L3 | 枝状管网流量分配 | 中高 | 第二阶段 |
| L4 | 环状管网平衡、复杂控制元件 | 中 | 暂缓 |
| L5 | 从 DWG/BIM 自动识别拓扑 | 中低 | 暂缓 |

主要风险：

- 管材实际内径、粗糙度和局部阻力数据不统一；
- 不同系统的取值及校核条件不同；
- 图纸上的公称规格不等于计算内径；
- 自动识别管网拓扑的工作量会超过公式开发。

### 3.2 负荷计算

### 判断：分类型看，汇总类高可行，动态建筑负荷不适合自研起步

| 类型 | 可行性 | 判断 |
|---|---:|---|
| 已知分项负荷的汇总、同时系数处理 | 高 | 适合首批扩展 |
| 电气负荷表批量计算 | 高 | 规则和样本明确时可快速实现 |
| 给排水设计流量汇总 | 中高 | 取决于系统类型和参数依据 |
| 消防用水量及系统需求汇总 | 中 | 责任风险高，应晚于普通模块 |
| 房间逐时冷热负荷 | 中低 | 输入量大、边界复杂，不建议从零自研 |
| 全年建筑能耗模拟 | 低 | 不属于首期范围 |

逐时冷热负荷和全年能耗已有成熟引擎。OpenStudio SDK 提供 EnergyPlus 的稳定、版本化接口，并有 Python 绑定；EnergyPlus 本身包含 HVAC sizing simulation 和相关输出。[OpenStudio 官方说明](https://openstudio.net/)、[EnergyPlus Engineering Reference](https://energyplus.net/assets/nrel_custom/pdfs/pdfs_v24.2.0/EngineeringReference.pdf)

据此，更合理的策略是：

- 对简单汇总类负荷自行实现；
- 对逐时冷热负荷优先复用成熟引擎或商业软件结果；
- 本项目负责标准化输入、结果提取、批量复核和报告，不重写完整热工模拟器。

主要风险：

- 围护结构、气象、使用时间表等输入工作量很大；
- 设计条件及方法差异会造成“同名负荷”含义不同；
- 若没有权威基准模型，程序结果难以验收。

### 3.3 设备选型

### 判断：算法可行，数据是瓶颈

设备选型可拆为：

1. 由计算模块生成设计需求；
2. 根据硬约束排除不满足的型号；
3. 按余量、效率、噪声、尺寸或价格等指标排序；
4. 输出满足项、不满足项和数据来源。

筛选和排序本身技术难度不高。困难主要在设备数据：

- 不同厂家的字段、单位和工况定义不同；
- 同一型号的样本版本可能变化；
- 部分性能需要曲线插值，不能只比较额定点；
- 缺少统一、稳定、可合法使用的数据接口；
- 设备可售状态、地区版本和选配条件会变化。

厂家自己的工具已经能基于流量、扬程等工况选泵，并同时考虑材料、连接、密封等条件。[Grundfos 官方产品资料](https://api.grundfos.com/literature/Grundfosliterature-2838929.pdf)

因此首期不应追求“全厂家自动选型”。建议：

- 先完成“设计需求计算”和设备数据模板；
- 只录入使用者实际常用的 1～2 个品牌/系列；
- 每条设备记录保留厂家、系列、型号、样本名称、版本或日期；
- 输出“候选清单”，不输出不可解释的唯一推荐；
- 厂家最终选型软件仍作为交叉校核渠道。

### 3.4 DWG/BIM 联动

### 判断：有价值，但不属于最小可用版

当前工作区有建筑、电气、结构和给排水 DWG，可以证明图纸是实际数据来源之一；但目录内没有标准化计算表或可验证样本。

从图纸自动提取房间、管线、长度和拓扑，理论上能显著减少录入；商业软件也把这一点作为核心能力。问题是：

- DWG 对象可能来自不同插件或已被转成普通线；
- 图层、块名、管径标注和系统命名不稳定；
- 平面图不能天然表达所有立管、连接和设备关系；
- 识别错误很难做到完全自动发现。

建议顺序：

1. 先支持标准 Excel/CSV；
2. 再支持从 CAD 导出的表格；
3. 最后只对高度标准化的图层/块做半自动识别；
4. 不承诺首期“打开任意 DWG 自动计算”。

## 四、技术方案可行性

### 4.1 推荐架构

```text
Excel/CSV 或页面录入
        ↓
字段校验与单位换算
        ↓
纯计算核心（不依赖界面）
        ↓
约束校核与候选筛选
        ↓
结果、警告、中间过程
        ↓
Excel 汇总表 / 计算书
```

### 建议组件

| 能力 | 首选 | 原因 |
|---|---|---|
| 计算核心 | Python 纯函数 | 易测试、易复用 |
| 批量数据 | pandas | 表格处理成熟 |
| Excel 输出 | openpyxl | 可直接读写 xlsx/xlsm 等格式，[官方文档](https://openpyxl.readthedocs.io/en/stable/index.html) |
| 物性 | CoolProp（按需） | 避免重复实现复杂物性 |
| 网络求解 | 自研简单枝状网络；复杂网络评估 pandapipes | 控制首期复杂度 |
| 本地界面 | Streamlit | 支持表格编辑、文件上传和下载，[官方数据编辑器](https://docs.streamlit.io/develop/api-reference/data/st.data_editor)、[官方文件上传说明](https://docs.streamlit.io/develop/api-reference/widgets/st.file_uploader) |
| 测试 | pytest | 适合基准样本和回归测试 |
| 参数存储 | 首期 YAML/CSV | 可读、可审查，暂不需要数据库 |

### 为什么首期不用大型数据库

首期数据量小，使用者少，核心风险是计算正确性而不是并发和容量。YAML/CSV 更便于工程师直接检查参数。设备量上升、多人并发或需要权限后，再迁移数据库。

### 4.2 计算核心必须与界面分离

每个模块应有独立接口：

```text
输入模型 → 校验 → 计算 → 结果模型
```

不能把关键公式直接写在 Excel 单元格或页面回调中。这样才能：

- 使用同一核心支持单项、批量和网页入口；
- 对每个样本自动回归；
- 修改界面时不改变计算结果；
- 清楚记录模块版本。

### 4.3 本地部署可行

首期可在 Windows 本机运行：

- 不需要上传项目图纸或计算数据；
- 可直接读取本地 Excel；
- 无服务器及账号维护；
- 便于先验证工作流。

如果后期多人使用，再评估局域网部署。云端部署涉及图纸、项目数据、账号和备份，不应作为首期前提。

## 五、投入估算

以下为单人开发配合专业工程师校核的经验级估算，不是固定工期。

| 阶段 | 工作内容 | 预计投入 |
|---|---|---:|
| P0 | 定义模块、整理字段、收集样本、核实参数来源 | 3～5 人日 |
| P1 | 单管段计算核心、校验、单位、自动测试 | 4～7 人日 |
| P2 | 批量 Excel 输入输出、最不利路径汇总 | 4～7 人日 |
| P3 | 本地页面、计算过程展示、计算书 | 3～5 人日 |
| P4 | 1 类设备需求计算和候选筛选 | 5～10 人日 |
| 合计 | 一个完整的验证版 | 19～34 人日 |

其中专业工程师的样本准备和结果复核不能由程序员替代。

若直接做多专业综合平台，预计进入 3～6 个月以上的持续开发，并产生长期参数维护工作；当前没有足够证据证明这种投入合理。

## 六、收益与回收期

建议不用“功能数量”衡量收益，而记录真实使用数据：

- 每月计算次数；
- 当前单次准备、计算、校核和出表时间；
- 自动化后单次时间；
- 错误返工次数；
- 模板维护时间。

### 计算方式

```text
月节省工时
= 每月使用次数 ×（原单次耗时 - 自动化后单次耗时）

回收期（月）
= 开发与校核总工时 ÷ 月节省工时
```

示例仅用于判断量级：

- 每月使用 20 次；
- 每次净节省 45 分钟；
- 则每月节省约 15 小时；
- 若验证版总投入 80～120 小时，静态回收期约 5～8 个月。

这个示例不包含减少错误和复核加快带来的收益。若实际每月使用不足 5 次，且每次仅节省十几分钟，则不值得开发独立模块。

## 七、主要风险

| 风险 | 概率 | 影响 | 控制措施 |
|---|---:|---:|---|
| 没有可靠基准样本 | 高 | 高 | 未取得样本前只做原型，不发布正式结果 |
| 参数或依据版本混用 | 中 | 高 | 参数独立存储，记录来源及版本 |
| 公式适用范围被忽略 | 中 | 高 | 明确适用/不适用范围，越界直接警告 |
| 设备数据过期 | 高 | 中高 | 记录样本日期，设置复核状态 |
| 一开始覆盖过多专业 | 高 | 高 | 每次只验收一个闭环 |
| 结果正确但输入成本过高 | 中 | 高 | 原型阶段计时，未节省时间则停止 |
| 页面好用但计算不可复核 | 中 | 高 | 强制输出中间值和采用参数 |
| 对 DWG 自动化预期过高 | 高 | 中高 | 先表格，后半自动识别 |
| 关键模块缺少专业复核 | 中 | 高 | 正式发布前由专业人员签认基准样本 |

### 消防、人防等高责任模块

这些模块技术上能编码，但不宜作为首批试验对象。原因不是公式一定更复杂，而是输入遗漏、适用范围判断和参数版本错误造成的后果更严重。应在公共计算框架、版本管理和回归测试成熟后再做。

## 八、立项闸门

### Gate 1：允许开始原型

必须同时满足：

- 明确一个计算模块；
- 至少有 3 份真实计算样本；
- 能说清输入、输出及适用范围；
- 能找到并实际核实参数来源；
- 该任务每月至少发生数次，或单次耗时明显。

### 当前状态

- 项目方向：已明确；
- 第一个模块：未最终确认；
- 真实计算样本：当前目录未发现；
- 参数来源：未建立；
- 使用频率和耗时：未记录。

因此，当前可以做需求原型，但尚不满足正式计算核心的开发条件。

### Gate 2：允许内部使用

- 3～5 份正常样本全部通过；
- 临界值、错误输入和极端值测试通过；
- 每项关键参数可追溯；
- 计算书可由另一位工程师独立复核；
- 自动化后确实节省时间。

### Gate 3：允许扩展第二个模块

- 第一个模块连续使用至少 1 个月；
- 没有未解释的结果偏差；
- 至少发生 10 次真实使用；
- 参数维护成本可接受；
- 用户确实需要下一个模块。

## 九、推荐实施方案

### 第 1 周：只做需求验证

1. 从近期工作中列出 5 个重复计算任务；
2. 记录每项每月次数、单次耗时、错误风险；
3. 按现有优先级模型评分；
4. 选得分最高且样本齐全的一项；
5. 将 3～5 份样本脱敏后放入 `data/examples/`；
6. 将经实际文件核实的依据索引放入 `data/references/`。

### 第 2～3 周：完成最小闭环

1. 定义输入和统一单位；
2. 编写纯计算函数；
3. 建立基准样本回归测试；
4. 制作批量输入模板；
5. 输出结果、警告和中间过程；
6. 生成计算书；
7. 与人工结果及一款成熟软件交叉核对。

### 第 4 周：真实项目试用

1. 用一个真实项目并行跑原流程和自动化流程；
2. 记录总耗时和人工修正点；
3. 对偏差逐项归因；
4. 达到 Gate 2 才转入内部使用；
5. 未节省时间或无法稳定校核则停止扩展。

## 十、最终建议

### 建议做

- 做面向个人/小团队的轻量计算流水线；
- 优先做表格批量计算和可复核输出；
- 从管径、阻力或负荷汇总类模块开始；
- 复用成熟物性和模拟引擎；
- 只维护实际使用的少量设备数据；
- 用真实工时和使用次数决定是否扩展。

### 暂时不做

- 多专业一体化平台；
- 自研完整逐时冷热负荷引擎；
- 任意 DWG 自动识别并直接计算；
- 全厂家设备自动选型；
- 消防、人防等高责任模块作为首发；
